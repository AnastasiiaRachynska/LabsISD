\section{Introduction}

\subsection{Purpose}
This Software Requirements Specification (SRS) defines the agreed scope, externally observable behavior, quality attributes, acceptance criteria, and behavioral scenarios for the Writer's Creative Ideas Information System. It is intended for the project owner, analysts, designers, implementers, testers, and academic reviewers. Requirement identifiers are stable references for specifications, tickets, tests, and implementation traceability.

\subsection{Scope}
The product is an offline-first smartphone client backed by a server application and REST API. Writers can capture, organize, link, search, and export literary creative material. A user can manage Books and Chapters, create Entries with preset Entry Types and Tags, associate Entries with Books and Chapters, and link Entries to one another. The client persists a local working copy in SQLite, supports core workflows without a network connection, and synchronizes changes with the server when connectivity is available.

The MVP client is limited to iOS and Android. A web client, desktop client, manuscript editor, multi-user collaboration, publishing workflow, and complex project/deadline management are out of scope. Server-backed data access and synchronization are in scope; account and authentication behavior is not specified in this revision. Text export to device-local storage is included.

\subsection{Intended Audience and Reading Guidance}
Section 2 describes context, users, platform, and constraints. Section 3 contains the normative functional and non-functional requirements. Section 4 defines acceptance evidence for every requirement. Section 5 specifies representative Given--When--Then (GWT) behavioral scenarios. Requirements use the word ``shall'' to indicate a mandatory product obligation.

\subsection{Definitions}
\begin{description}
  \item[Book] A user-created container for creative material belonging to a literary project.
  \item[Chapter] A named subdivision of a Book. Entries may be associated with a Chapter and with the Chapter's parent Book.
  \item[Entry] A piece of creative material managed by the system. ``Note'' is a user-facing synonym, not a separate data entity.
  \item[Entry Type] The preset primary classification of an Entry: Character, Scene, Plot Idea, World-building, Dialogue/Phrase, or General Note.
  \item[Tag] A user-applied flexible label that supplements, and does not replace, an Entry Type.
  \item[Standalone Entry] An Entry with no current Book or Chapter associations.
  \item[Book Association] A direct relationship between an Entry and a Book as a whole.
  \item[Chapter Association] A relationship between an Entry and a Chapter. It automatically implies association with the Chapter's parent Book. A direct Book Association is tracked separately.
  \item[Entry Link] An unlabeled, symmetric relationship between two Entries, distinct from Book and Chapter associations.
  \item[Quick Capture] The workflow for creating an Entry with minimal required input. A General Note can be created with Content only.
  \item[Display Title] The title shown for an Entry. It is the explicit Title when nonblank; otherwise, it is derived from Content under REQ-F-003.
  \item[Book Project Export] A text export of a Book and the Entries associated with it directly or through its Chapters.
  \item[Pending Change] A locally persisted create, update, or delete that has not yet been acknowledged by the server.
  \item[Sync Cursor] An opaque server-issued position used by a client to request changes made since its previous synchronization.
  \item[Sync Conflict] A server-side version conflict in which the same record was changed locally and remotely since the client's last synchronization.
\end{description}

\section{Overall Description}

\subsection{Product Perspective}
The product uses a mobile client and a server application. The client maintains a durable local SQLite working copy via Expo SQLite, communicates with the server through a versioned REST API, and synchronizes pending local changes and server changes when connected. The mobile operating system provides the runtime, accessibility services, and local file handling used for text export. While offline, the client continues to use its local data and queues changes for later synchronization.

\subsection{Product Functions}
At a high level, the product provides:
\begin{itemize}
  \item quick capture and lifecycle management of Entries;
  \item preset Entry Types and user-defined Tags;
  \item Book and Chapter organization, including many-to-many Entry-to-Book association;
  \item automatic parent-Book association for Chapter-associated Entries;
  \item symmetric links between Entries;
  \item case-insensitive full-text search and combined search/type/tag filtering;
  \item local text export of an Entry or Book project;
  \item synchronization of local changes to the server and retrieval of remote changes; and
  \item internal local diagnostic logging without a dedicated user-facing log interface.
\end{itemize}

\subsection{User Classes and Characteristics}
The primary user class is an individual writer, novelist, screenwriter, or storyteller who needs to capture ideas on the move and later organize and retrieve a large volume of heterogeneous creative material. The MVP has one local user context per device; account identity, authentication, and multi-user behavior are not defined.

\subsection{Operating Environment}
\begin{itemize}
  \item Mobile application developed with React Native, Expo, and TypeScript.
  \item Android 10.0 or later (API level 29 or later).
  \item iOS 15.0 or later.
  \item Minimum supported logical viewport: 360 by 640 device-independent pixels (dp).
  \item On-device SQLite persistence using \texttt{expo-sqlite}, with a remote server reachable over HTTPS when connected.
  \item Core application workflows must function without network connectivity; synchronization requires network connectivity.
\end{itemize}

\subsection{Design and Implementation Constraints}
\begin{itemize}
  \item The MVP client is mobile-only; web and desktop clients are excluded.
  \item The client shall retain a local working copy; the server is the shared synchronization endpoint when the network is available.
  \item The REST API transport and payload format shall follow the communications requirements in Section 3.
  \item Authentication, account lifecycle, and multi-user access control are not specified by this revision.
  \item The Entry Types are a fixed preset set. Flexible categorization is provided by Tags, not user-created Entry Types.
  \item Book and Chapter deletion must not cascade into deletion of Entries.
  \item Entry Links are unlabeled and symmetric.
  \item The codebase shall use TDD and meet the coverage thresholds in REQ-NF-014.
\end{itemize}

\subsection{User Documentation}
In-app help content, onboarding, and end-user documentation are not specified by the approved MVP decisions. Their inclusion and format remain for project planning.

\subsection{Assumptions and Dependencies}
\begin{itemize}
  \item The device has functional local storage and an operating-system-supported means of saving or selecting a local destination for exported files.
  \item Availability of a file destination or permission may vary by platform; export failure must be reported as specified.
  \item Normal operating conditions for performance measurement, export text layout, diagnostic-log retention, and some detailed matching behavior require a verification/design decision; these are recorded in Section 6 rather than silently assumed.
\end{itemize}

\section{Specific Requirements}

\subsection{External Interface Requirements}
\subsubsection{User Interface}
The interface shall be designed for small smartphone screens and quick on-the-go capture. It shall provide workflows to create and manage Entries, Books, Chapters, Tags, and Entry Links; retrieve Entries; and initiate exports. Detailed screen layouts, navigation structure, and visual design are outside this SRS.

\subsubsection{Software Interfaces}
The mobile client shall use React Native, Expo, TypeScript, and \texttt{expo-sqlite} for local relational persistence. It shall use platform capabilities as needed for local text-file export and accessibility. The client shall communicate with the backend REST API described below.

\subsubsection{Communications Interfaces}
Client-server communication shall use HTTPS. API requests and responses shall use UTF-8 encoded JSON and RESTful resource semantics. The versioned API base path shall be \texttt{/api/v1}. Resource endpoints shall include \texttt{/entries}, \texttt{/books}, \texttt{/chapters}, \texttt{/tags}, \texttt{/entry-tag-associations}, \texttt{/entry-book-associations}, \texttt{/entry-chapter-associations}, and \texttt{/entry-links}; standard HTTP methods shall be used to create, retrieve, update, and delete resources. Synchronization shall use \texttt{POST /api/v1/sync/push} for client changes and \texttt{GET /api/v1/sync/pull?cursor=\{cursor\}} for server changes. Requests shall be independently processable and responses shall use HTTP status codes to report success, validation errors, and version conflicts. The client shall not require network access for core capture, organization, search, or export workflows.

\subsubsection{Data and Export Interface}
The local database shall represent Entries, Books, Chapters, Tags, Book Associations, Chapter Associations, Entry Links, pending changes, synchronization metadata, and diagnostic events. API resource representations shall identify the resource and its relationships and carry version information needed to detect concurrent changes. Synchronization responses shall identify acknowledged changes, remote changes, deletions, and the next Sync Cursor. Export output shall be a \texttt{.txt} file saved to device-local storage. UTF-8 encoding is required. Exact export metadata, punctuation, and file-naming conventions remain unspecified.

\section{Behavioral Scenarios (Given--When--Then)}
The following scenarios are representative acceptance-level examples. They complement, but do not exhaust, the acceptance criteria above.

\subsection*{Scenario 1: Generate a Display Title}
\textbf{Given} an Entry is created with a blank Title\\
\textbf{When} the user saves Content\\
\textbf{Then} the system generates a Display Title whose body is limited to the first 25 characters\\
\textbf{And} if the Content exceeds 25 characters or a newline occurs within the first 25 characters, the system appends ``...'' after the retained body, outside the 25-character limit\\
\textbf{And} no text after the first newline appears in the Display Title.

\subsection*{Scenario 2: Create an Entry with All Details}
\textbf{Given} the user is creating an Entry and has entered an explicit Title and Content, selected an Entry Type, and added Tags\\
\textbf{When} the user saves the Entry\\
\textbf{Then} the Entry is saved with the entered Title and Content, selected Entry Type, and Tags\\
\textbf{And} viewing the Entry shows those saved values without replacing the explicit Title with a generated one.

\subsection*{Scenario 3: Chapter and Book Associations}
\textbf{Given} an Entry's only Chapter Association in Book A is to the Chapter being deleted, and it is also directly associated with Book B\\
\textbf{When} the user deletes that Chapter\\
\textbf{Then} the Entry remains available and its association with Book B remains\\
\textbf{And} it is no longer associated with the deleted Chapter or its Chapter-derived Book A association.

\textbf{Given} an Entry has no association other than one with a Chapter\\
\textbf{When} the user deletes that Chapter\\
\textbf{Then} the Entry remains available as a Standalone Entry.

\textbf{Given} an Entry is associated with a Book\\
\textbf{When} the user deletes that Book\\
\textbf{Then} the Entry remains available and is detached from the deleted Book.

\subsection*{Scenario 4: Symmetric Entry Links}
\textbf{Given} Entries A and B exist and are not linked\\
\textbf{When} the user links A to B\\
\textbf{Then} B appears in A's links and A appears in B's links.

\textbf{When} the user removes the link from either Entry\\
\textbf{Then} the link no longer appears for either Entry, and both Entries remain available.

\subsection*{Scenario 5: Search and Combined Filters}
\textbf{Given} Entries contain matching text in their Titles or Contents using different letter cases\\
\textbf{When} the user searches for that text\\
\textbf{Then} all Entries with a case-insensitive match in either field appear, and Entries without a match do not.

\textbf{Given} Entries have different Entry Types and Tags\\
\textbf{When} the user applies a search term, multiple Entry Type values, and multiple Tag values together\\
\textbf{Then} each result matches the search term and every selected Entry Type and Tag\\
\textbf{And} Entries that fail any one of these criteria do not appear.

\subsection*{Scenario 6: Export Book Project in Chapter Order}
\textbf{Given} a Book has Chapters in sequential order, Entries associated with those Chapters, and Entries associated directly with the Book\\
\textbf{When} the user exports the Book project\\
\textbf{Then} Chapter-associated Entries appear under their respective Chapter headings, with Chapters sorted by ascending internal position when available and otherwise by ascending \texttt{created\_at}\\
\textbf{And} Entries associated directly with the Book but not placed under a Chapter appear in a dedicated ``General Book Notes'' section at the end\\
\textbf{And} an Entry associated with both a Chapter and the Book appears once, under its Chapter heading.

\subsection*{Scenario 7: Offline Use and Persistence}
\textbf{Given} the device has no network connection\\
\textbf{When} the user creates and organizes an Entry, searches for it, and exports it\\
\textbf{Then} these operations use local data and complete without network access.

\textbf{When} the user closes and reopens the app while still offline\\
\textbf{Then} the Entry and its saved Content remain available and its changes remain queued for synchronization.

\textbf{When} network connectivity is restored\\
\textbf{Then} the queued changes are synchronized with the server without requiring the user to recreate the Entry.

\subsection*{Scenario 8: Create and Structure a General Note}
\textbf{Given} the user has an idea to capture\\
\textbf{When} the user creates a General Note with Content only\\
\textbf{Then} the Entry is saved as a General Note without requiring a Title, Tag, Book, or Chapter.

\textbf{When} the user later changes its Entry Type, adds a Tag, and associates it with a Book or Chapter\\
\textbf{Then} those changes are saved and displayed when the Entry is viewed again.

\subsection*{Scenario 9: Export Success and Failure}
\textbf{Given} an Entry contains representative accented and non-Latin text\\
\textbf{When} the user successfully exports the Entry\\
\textbf{Then} a \texttt{.txt} file is available in device-local storage and preserves the text when decoded as UTF-8.

\textbf{Given} a local storage error prevents an export from completing\\
\textbf{When} the user attempts the export\\
\textbf{Then} the app reports the failure and does not indicate that the export succeeded.

\subsection*{Scenario 10: Delete an Entry}
\textbf{Given} an Entry exists and is linked to another Entry\\
\textbf{When} the user deletes the Entry\\
\textbf{Then} the deleted Entry is absent from Entry lists and search results\\
\textbf{And} no active Entry Link points to the deleted Entry\\
\textbf{And} the other linked Entry remains available.

\subsection*{Scenario 11: Server API Resource Management}
\textbf{Given} the client is connected to the backend API\\
\textbf{When} the client creates, retrieves, updates, and deletes Entries, Books, Chapters, and Tags using their API resources\\
\textbf{Then} each successful operation returns or reflects the expected JSON resource state\\
\textbf{And} creating or removing associations and Entry Links through their resources preserves the relationship rules and leaves no dangling references.

\subsection*{Scenario 12: Offline Change Synchronization}
\textbf{Given} the client has queued local creates, updates, and deletions while offline\\
\textbf{When} connectivity is restored and the client pushes its pending changes and pulls server changes from its saved Sync Cursor\\
\textbf{Then} acknowledged local changes are applied once and remote changes, including deletions, are applied to the local store\\
\textbf{And} unacknowledged changes remain queued for retry\\
\textbf{And} the new Sync Cursor is persisted with the applied changes.

\subsection*{Scenario 13: Resolve a Synchronization Conflict}
\textbf{Given} a record was changed both locally and on the server since the client's last synchronization\\
\textbf{When} the client submits its outdated version\\
\textbf{Then} the server reports a version conflict and the client preserves and displays both versions\\
\textbf{When} the user selects which version to retain\\
\textbf{Then} the selected version is submitted as a new change and synchronized.

\section{Traceability and Outstanding Specification Details}
The acceptance criteria are keyed directly to requirement identifiers. Functional criteria \texttt{AC-F-001} through \texttt{AC-F-037} map one-to-one to \texttt{REQ-F-001} through \texttt{REQ-F-037}; non-functional criteria \texttt{AC-NF-001} through \texttt{AC-NF-015} map one-to-one to \texttt{REQ-NF-001} through \texttt{REQ-NF-015}. The GWT scenarios exercise key cross-requirement workflows and cite the same observable behavior. The accompanying RTM maps each requirement to its acceptance criterion and relevant scenario or verification evidence.

The following details were not decided during SKED and must be specified in the design, verification plan, or a later SRS revision before their related checks can be fully reproducible:
\begin{itemize}
  \item whether users can manually reorder Chapters, beyond the export ordering rule specified in REQ-F-028;
  \item exact text layout, metadata, file naming, and platform destination-selection behavior for exports;
  \item diagnostic-log redaction and timestamp precision;
  \item account identity, authentication, and authorization behavior, which are outside this revision's specified scope; and
  \item the precise definition of domain logic and repository code included in the REQ-NF-014 coverage scope.
\end{itemize}
